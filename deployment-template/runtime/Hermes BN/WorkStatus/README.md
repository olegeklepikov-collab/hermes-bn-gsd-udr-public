# Краткие статусы всей работы Hermes BN

Подключён `bn-work-status 1.0.1` в главном профиле, `bn-gsd-only` и `bn-udr-only`. Исходный Hermes и GSD не изменены. Статусы не дают разрешений, не запускают новые задания и не вызывают модель отдельно.

Порядок общения: цель и ближайшие этапы перед первым действием; затем «Завершено → Сейчас → Следующее». Наблюдатель отдельно сообщает подготовку вызова, получение ответа, ошибку, запрос запуска дочернего исполнителя, начало его обработки и завершение. Продукт исполнителя и принятие вывода различаются. Параллельные активные шаги перечисляются кратко, одинаковые операции группируются с числом экземпляров. Во время длительной обработки статус повторяется не чаще раза в минуту.

Нативные промежуточные сообщения и комментарии включены. Служебные аргументы, ключи, внутренние рассуждения и полные результаты в автоматические статусы не включаются. Начало следующего шага содержит последний завершённый шаг. Подготовительные операции объединяются, чтобы не повторять технические сообщения о получении схем.

Использованы предусмотренные `pre_llm_call`, `pre_tool_call`, `post_tool_call`, `subagent_start`, `subagent_stop`, `post_llm_call`, профильный `PluginState`. Тонкий адаптер использует экспортированный `get_active_subagent_parent` и публичный параметр агента `status_callback`; источник интерфейса — установленный Hermes 0.21.5. Доставка идёт через обычный шлюз в текущий разговор; новые пользовательские ходы не создаются, отдельный токен Telegram не нужен.

Состояние текущего и последнего хода хранится в профильном `plugin-data/agent-plugin-bn-work-status-e76e2bd7/state.json` с правами владельца. Это состояние отображения, а не второй учёт задач: Beads остаётся основным учётом. После неожиданной остановки незавершённый ход обозначается как требующий проверки; его действия не повторяются автоматически. Состояние разных профилей изолировано. В программном тихом CLI вывод статусов намеренно подавлен режимом клиента; сохранённое состояние остаётся доступным.

Проверки: четыре поведенческих условия — переходы и ошибки без утечки аргументов, устаревшие/повторные события и исполнители, сохранение/изоляция A→B→A/минутный статус, параллельные шаги. Реальный CLI последовательно проверил состояние семьи и движка. Реальный Telegram показал переходы G/S/D и начало/завершение отдельной проверки UDR; G/S/D подтверждены действительными квитанциями. Первое живое испытание выполнялось на 1.0.0; 1.0.1 уточняет запрос запуска, начало обработки и параллельное отображение и проверен отдельно настоящим G, затем отдельной проверкой состояния семьи: сообщения о подготовке, фактической обработке, результате и следующем этапе получены в интерфейсе Telegram.

Граница: при отсутствии сети доставка сообщения не гарантируется; состояние сохраняется локально. Нативный callback ставит сообщение в отправку, а не подтверждает его получение. Подтверждение живого Telegram получено чтением интерфейса. Служебные фоновые проходы без пользовательского хода не выдаются за этапы пользовательской задачи. Новая команда, прерывающая работу ради чтения статуса, не добавлялась.

Установка: Python этого Hermes → `WorkStatus/releases/1.0.1/install.py --root "ПУТЬ/Hermes BN"`, при остановленном собственном шлюзе. После установки запустите шлюз и приложение. Контрольные суммы изменённых модулей включены в настройки допуска GSD. Изменения конфигурации и согласованный путь сохранены в `WorkStatus/operator/checkpoint-*`.

Откат: остановите собственный шлюз, восстановите только конфигурацию и настройки допуска из нужного checkpoint по manifest.json; сохранённые рабочие данные и учёт не заменяйте. Затем запустите службы. Модуль, оставленный на диске, при снятии его enabled не выполняется.
